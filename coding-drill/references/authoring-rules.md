# 出题纪律：怎样出一道“薅不到分”的编程题

这些规则来自我们自己两轮各数百道题的实测：没有纪律约束时，一个只打印常量、根本不读输入的程序平均能拿 **48.8%** 的分；按这套规则重出后常量拿 **0 分**，但“把输入原样打印一个 token”仍能在 **11.2%** 的题上得分——直到加上“至少一条隐藏用例的答案不在输入里”这条规则。问题从来不在模型，在于没人替出题过程设闸门。规则不多，每条都对应一种真实的漏分方式。

## 1. 题的形态

- **完整程序、标准输入 → 标准输出**。不是补函数签名。题面必须写清输入格式、输出格式，并给一组与样例用例完全一致的示例。
- 输出只用整数、`true`/`false`、单词，或它们的多行组合。**不输出浮点数**（跨语言格式不稳，脚本会拒绝）；要小数就改问整数：个数、总和、取整。
- 输出的任一行不以空格结尾；比对模式是 `trim`（只去整段输出首尾空白），行内多余空格会判错。
- 答案唯一。答案是“位置”或“元素”时补一句并列规则（“多个符合时取下标最小的”）。
- 确定性：不用随机数、时间、语言相关的散列顺序。
- 数据规模小：一维 n ≤ 100，二维行列各 ≤ 12 且行数 ≠ 列数（防止把行数当列数用而不被发现），数值 ≤ 100000，每条用例的输入不超过 20 行。一条用例应在几毫秒内跑完。
- 输入格式统一：变长列表前先给一行个数；一维列表一行、空格分隔；二维先给 `r c`，再给 r 行；标量参数（阈值、目标）放最后一行。

## 2. 用例形状：1 + 4

一道题 10 分：**1 条样例（0 分）+ 4 条隐藏用例（2 + 3 + 2 + 3，3 分给最有诊断力的两条）**。需要第 5 条隐藏用例时只允许 2 + 2 + 2 + 2 + 2。脚本要求隐藏用例恰为 4 或 5 条。

样例分值必须为 0：判题不区分样例与隐藏，样例的输入输出学生都看得见，给分等于白送。

## 3. 用例职责（job）——样例 1 条，隐藏 4 条各取一个不同职责

| 职责（job） | 内容 |
|---|---|
| `sample` | **样例专用，隐藏用例不可用。** 最小的、仍能说明规则的实例；与题面示例逐字一致 |
| `typical` | 答案在与样例不同的位置——比如在数据最末尾 |
| `boundary` | 恰好等于阈值的值；第一个/最后一个元素；只有一个元素 |
| `empty` | 什么都不匹配，答案是“没找到”的值（`0`、`-1`、`NONE`） |
| `saturated` | 全部匹配，或允许的最大规模 |
| `order` | 多个候选符合，只有第一个（或最后一个）是答案 |

四条隐藏用例取**四个不同的职责**（题目没有“没找到”的情形就换一个职责），脚本会检查职责两两不同。**每条用例只改一件事**：同时改了规模、数值、正负号的用例，挂了也说明不了什么。

## 4. 让它薅不到分——按构造保证

1. 所有用例的期望输出**两两不同**。
2. 所有用例的输入两两不同且非空；**没有任何一条用例的输出等于它自己的输入**。
3. 没有任何一条用例的期望输出为空（空程序会过）；也不能等于起步骨架里占位返回的值（原样提交的骨架会过）。
4. 自问：**一个完全不读输入的程序能过任何一条隐藏用例吗？** 能就改数据。脚本会跑四个非解验证：打印样例输出、什么都不打印、原样回显输入、**起步骨架原样提交**——四个都必须 0 分；再跑“只打印输入的一个 token 或一行”的四个非解（见第 7 条）与几个常量（见第 8 条）。
5. **每个阈值上必须坐着一条计分用例。** 题面说“至少 goal”，就要有一条用例的值恰好等于 goal；否则 `>` 和 `>=` 无法区分，最常见的错误看不见。
6. 如果程序返回的是和输入同类型的东西（列表进列表出、字符串进字符串出），至少一半的分要放在“答案不是输入原样”的用例上。
7. **至少一半的分要放在“答案不是输入里任何一个 token、也不是输入的任何一行”的用例上。** 求最大值、取最后一个元素这类题，一个只打印输入某个 token 的程序就能拿分——这就是 11.2% 那个漏洞。脚本会跑“打印第一个 / 最后一个 token、第一行 / 最后一行”四个非解，任一拿到一半以上的分就不合格。
8. “没找到”的答案别用太好猜的值：一个只打印 `0` 或 `-1` 的程序，会恰好过掉 `empty` 那条用例。期望输出两两不同保证了一个常量最多过一条，但那一条也不该白送——能改就改成不那么好猜的值，或把分放在别的用例上。
**常见死角（答案是下标或计数时）**：`saturated`“全部匹配”的答案往往是 `n` 或 `1`，`typical`“答案在末尾”的答案往往等于第一行的 `n`——前者撞常量基线，后者撞“打印第一行 / 第一个 token”基线。解法：把“没找到”改成 `NONE` 这类词而不是 `0` / `-1`；让答案落在数据中间的位置；计数题让个数与 `n` 错开（比如 n=6 时答案是 4，不是 6 或 1）。先想清楚每条用例的答案会不会恰好等于输入里的某个数，再定数据。
9. 隐藏用例的期望输出**只许由参考解实跑得到**，不许手写、不许猜、不许由脚本反过来“修正”参考解。样例那条可以手写你预期的值，用来交叉校验参考解；脚本发现两者不一致会报错，不会替你改。

## 5. 让它有诊断力——错解

每条隐藏用例写明它抓的是什么误解（`catches`，写具体的错法，不写“测试边界”这种类别），并附**至少 2 个、最好 3 个错解**：完整、能运行、像学生会写出来的程序，各实现一种误解。脚本会跑它们：

- 错解拿满分 → 这套用例看不见这个误解，题不合格。
- 好的错解**至少挂一条、也至少过一条**。挂光的错解只证明它是错的，不证明用例有针对性。
- 反过来看：**每条隐藏用例都应至少被一个错解挂掉**——一条谁都挂不掉的用例，说明它抓的那个误解没有对应的错解来证明，`catches` 只是写在那里。脚本会对这种用例报 WARN。

用例只有在错程序产出**不同输出**时才算抓到了误解：

- 要抓 `max = 0` 的初始化错误，数据必须**全是负数**；
- 要抓正向遍历时删元素导致跳过，必须有**两个相邻元素**都要删；
- 要抓行数列数混淆，行列必须**长度不同**；
- 要抓 `==` 比较字符串（Java）而不是 `equals`，被比较的字符串必须在**运行时拼出来**（短字面量会被缓存而侥幸通过）；
- 要抓 `>` 写成 `>=`，必须有值**恰好等于阈值**；
- 要抓循环边界差一，必须让**最后一个元素决定答案**。

## 6. 起步骨架与参考解

- 起步骨架能直接运行（含读输入的代码），**原样提交必须 0 分**；占位返回值（如 `-1`、`NONE`）不能是任何用例的期望输出。
- 骨架不泄露算法：不写半截实现，注释里不点破技巧。
- 参考解 = 骨架填完，读起来像一个好学生的答案，不是代码高尔夫——这是老师在学生质疑分数时要打开看的文件。
- Java：公开类名必须恰好是 `Main`，不写 `package`；Python 无第三方库；JavaScript 用 CommonJS，读 stdin 用 `require('fs').readFileSync(0, 'utf8')`。

## 7. 难度

自上而下取第一条匹配的：

| 值 | 条件 | 标志 |
|---|---|---|
| 3 | 对象之间有交互，或契约有多个特例，或嵌套循环的内层上界依赖外层下标 | 多个对象 / 类 + 算法；失败路径要保持状态不变；25 行以上 |
| 2 | 两个构造组合，或一个构造加一个要推理的边界（含一次矩形网格的嵌套遍历 + 一个累加器） | 遍历 + 累加；含 2～3 个成员的类；11～25 行 |
| 1 | 一个构造、一次遍历、没有相互作用的状态 | 单循环或单条件；≤ 10 行；没有边界微妙之处 |

难度要写一句理由（`difficultyReason`），不按“第几题”机械分配。

## 8. 时限

一律填 `2000`（毫秒）。只有当 `author` 报告显示参考解单条用例超过 300 ms 时，才提到 `3000`。

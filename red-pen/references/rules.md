# red-pen 批注纪律

这份文件讲的是**为什么**每一道闸门长成那样，以及闸门拦下来的时候该往哪边改。格式与键名在 `workspace-format.md`，那边是契约，这边是理由。

一句话：**红笔只许写在稿子的边上。** 批注必须指向稿子里真实存在的一句话，改法只许针对那一句；一旦你开始重写整段，你写的就不是批注，是另一篇稿子，而用户失去了判断的机会。六道闸门都是从这一句推出来的。

## 闸门一：没跑 `context` 就写不出批注

`inbox/marks.json` 的第一个键是 `context_hash`，它由稿子的纯文本加 brief 算出来。这个哈希只有一个来源——`context <slug>` 的输出。

它挡的是三件事：

- **凭印象批。** 上一轮对话里看过稿子，这一轮凭记忆写批注，引文就会似是而非。哈希对不上，先把稿子重新读一遍。
- **改了稿还用旧批注。** 用户改完一版，旧批注引的句子可能已经不存在了。哈希跟着稿子走，改一个字就作废。
- **改了标准还用旧批注。** brief 也进哈希。「给谁看」从同行换成家长，值得批的东西就变了，旧批注不该继续算数。

所以顺序是硬的：`context` → 写批注 → `review`。不要手抄哈希，从 `context` 的输出里原样取。

## 字怎么数

**口径。** 汉字、假名、谚文逐字计，连着的字母或数字算一个，标点与空白不计。全库只有这一把主尺：四道按字数算的闸（引文上限、批语下限、单条改法预算、改法合计预算）与 `init` 打印的正文字数，数的都是它。

**例子。** `Hi Dana,` 是 2 个字——两串字母各算一个，逗号不计；`问不清楚的先不报` 是 8 个字。靠多打几个空格、把直引号换成弯引号来凑长度是没用的：这把尺看不见标点，也看不见空白。

**护栏：这把尺与 `brief.lang` 无关。** `lang` 只管批语用哪种语言写，闸门的宽严一律不按它分流。三条理由，每一条单独都站得住：

- **契约写死了 `lang` 指的是批语的语言，不是稿子的语言。** 中文稿配英文批语是常事；真按 `lang` 分流，这种稿子会走英文那一档，而中文不靠空格断词，一句 28 个字的中文引文整句只数出 1 个词——比今天还惨。
- **`lang` 是 Agent 自己写得动的字段。** 把闸门的宽严挂在可写字段上，等于开了一条「把 `lang` 改成 `en` 就能拿到更宽预算」的道，与「闸门必须是确定性的」这条立身之本直接冲突。
- **换成字符串自身的函数之后，先后顺序的问题自动消解。** `init` 要打字数的那一刻 brief 还没写，按 `lang` 分流的尺在那里根本无从取值。

**这是一条永不做。** 写清楚是为了挡住下一个人「顺手」把闸门挂到 `lang` 上。

## 闸门二：形状——引文要真，批语要具体，改法要短

四条形状约束，各拦一种走偏：

**引文非空、不超过 200 字。** 批注必须挂在某一句上。引文越长越像在抄稿子而不是在指问题，200 字是上限不是目标——通常引一句话就够。引文还得是**原文里真有的那一句**，一字不差；这是提交时必须遵守的纪律。脚本保留规范化与头尾锚定兜底，所以顺手改字或标点并不保证被闸门三拦下；即便定位成功，也不能代替逐字核对来源。英文按词算（连着的字母或数字算一个），所以这一档对英文稿相当宽；另有一条 400 字符的原串硬顶接住整段引用那种极端情形。

**批语至少 6 个字。** 「不好」「再改改」不是批语。批语要说清**这一句**出了什么问题，而不是给稿子打分。英文同理：`Too vague.` 只有两个词，不够；说清「问题出在哪一句、哪个词」的一句话通常七八个词，够了。

**改法有预算：引文字数 × 3，最少 20 字、最多 40 字；也不能与引文相同。** 与引文相同意味着你没给改法，只是把原句复读了一遍。下限管短引文——英文两三个词的引文乘出来只有几个字，写不下一句可照抄的短句，所以短的那一侧给到 20 字；上限管长引文——40 字限制单条建议的长度，预算不再随着长引文一直放宽。但长度闸不能识别所有整段或整篇短稿重写，过了预算也仍须遵守不代笔的纪律。改法的作用是给方向和一个可照抄的短句，不是替用户下笔。不想给改法就把这个键去掉，别留空串。

**条数 1–30。** 一条都没有说明你没在批；超过 30 条，用户读批注比读稿子还累，该做的是挑出最要紧的那些。

**条数上限是纪律，不是技术限制。** 实测过它的一处空洞：稿子极短的时候，这道闸拦不住把一句话拆成好几条这种退化写法——短稿上真正管住条数的是作者自己，不是这个数。这里只记录、不加断言：条数闸与它的常量一个字不改，自测也不补用例；补了就等于承诺拦得住，而实测拦不住，记录比承诺诚实。下一轮若要处置，候选修法是「条数上限随稿子字数收窄」，但那是一道会让今天通过的工作区突然被拒的新闸门，**必须先量再上**。

## 闸门三：锚定率不到七成就重批

脚本会把每条引文拿去原文里找。钉不住的照样进结果，但会单独列在「未能定位」一节，**脚本绝不擅自把它摆到某个位置**——摆错地方比不摆更糟，用户会以为那句话就在那儿。

钉住的条数占七成以下，`review` 直接拒收，并把钉不住的原因、引文、批语逐条摊开。**先看原因再改**，不是删掉那几条凑比例，更不是改稿子去迁就引文；即使已过七成，成功输出也会逐条列出未定位条目，请原样念给用户。

**只有 1–3 条批注时，七成等价于零容忍。** 3 条里错 1 条就是约 0.67，已经在线下；5 条里错 1 条是 0.8，仍能过线。少量批注的锚定率会随一条的成败跨过门槛。输出保留「条数少的时候一条钉不住就等于整份不过：回原文把那一条重抄一遍就行，不必删条凑比例。」这句提示，具体处置仍按下面的原因来。

脚本按三种原因指路：

- 与别的批注重叠，脚本留了起点靠前的那条（同起点取长）；引文本身没问题，把这两条合成一条，或改引另一句。
- 这一句在稿子里逐字都有，但它横跨了两块（段落 / 列表项 / 表格行 / 标题之间）；脚本不做跨块锚定，只引其中一块。
- 稿子里找不到这一句；回 draft_text 一字不差地重抄。

结果里还有一种「头尾锚定」：引文只有开头（或结尾）对得上，脚本按引文长度推出一个区间并标出来。这种条目在红笔页上写着「仅供参考」，它是兜底不是正常态；看到它就说明那句引文抄得不够准，值得回去核一遍。它现在会出现在 `review` / `stats` 的输出与 `export` 里；头尾锚定条数 ÷ 已锚定条数 > 1/3 时，还会出一条只提醒不拦的 WARN。

**引擎不动重叠归约。** `anchored` 的含义是「页面上有没有这条的下划线」，重叠让位之后确实没有、也确实没有 `start` / `end`；把它改成真会让红笔页的分栏、`marks[].start` 的存在性、`check` 的逐字节复算三处同时说谎。信息一直都在 `dropped_overlap` 里，坏的是报错文案，本期补的就是那句话。

**不把重叠让位移出锚定率分母。** 移出去之后，提交两条互相重叠的批注就成了零成本，闸门失去压力；而且分母一变，三家 `anchored_ratio` 的历史数字口径就断了。现在的路是通的：把两条合成一条，条数 3→2、锚定率 0.67→1.0。

**下一轮谁拿着自查报告来改归约逻辑，先读这一段**——照那份报告改才是真正的回归。

## 闸门四：不许同一句批两遍，也不许一句评语贴两处

两条引文规范化后相同、或两条批语规范化后相同，整份拒收。

这道闸门还被 `review` 的编号对照依赖着（规范化引文互不相同，提交序才映射得回去），别放宽。这张映射靠闸门四（两条引文规范化后不许相同）才成立。闸门四一旦被放宽，同一个规范化引文会对应两个提交序，编号映射会**静默错位**，报错就会指着错的那一行让人去改。改闸门四之前先改这里。

引文重复说明你在同一句上反复打转；批语重复说明你在套模板——同一句「表达不够具体」贴到三个地方，用户三处都不知道该怎么动。真的是同一个毛病出现在两处，就把两处合成一条，在批语里说清「这个毛病在下面还犯了一次」，或者对着第二处写出它自己的问题。

规范化会把空白与引号、破折号的写法拉平，所以靠多打一个空格、把直引号换成弯引号来绕过这一条是没用的。

## 闸门五：批注全挤在开头，多半是没读完（提醒，不拦）

所有钉住的批注都落在稿子开头 20% 的篇幅里时，脚本会提醒一句。这是最常见的偷懒模式：开头三段批得很细，后面越来越少，最后一段干脆没碰。

这一条只是 WARN，不拦。稿子确实是前面问题密集就照常交，但交之前**自己回去确认一遍后半段真的读过**。

**前提是稿子分得出三块。** 不足三块的稿子上这条提醒不响：「前 20%」不足以判断一段话的公告有没有读完。块数按**块边界**数（段落、列表项、表格行、标题之间），**不是数换行符**——一段里连着敲了几个换行的公告仍然算一块。

块数这个量还有一处会偏少：HTML 稿里某一块的文字本身就以换行结尾时（缩进美化过的稿子最常见），那处真实的段落边界与块内软换行分不开，脚本会把两段当成一块（`workspace-format.md` 第 6 节写着这条边界）。偏少只往沉默那一侧偏——该响的提醒可能不响，不会反过来误报；引擎不为这件事改动。想避开它，把稿子存成 `.txt` / `.md` 收进来即可。

要注意它算的是**消毒后 HTML 的偏移**，不是「前 20% 的文字」。每段都套着容器的稿子里，标签也占长度，同一句话的偏移会显得比它在正文里的位置靠后，这条提醒因此偏保守：它不响不代表读完了，它响了也可能只是标签多。判断标准始终是你自己有没有把稿子看到底。

## 闸门六：改法合计超过稿子的一半就是重写

所有 `fix` 加起来的字数超过合计预算，整份拒收：预算为稿子字数的一半，短稿至少给到 60 字。预算只约束长度，不能保证识别所有整段或整篇短稿重写；不给整段重写的纪律仍须逐条遵守。

这一条对着的是最像帮忙、其实最有害的做法：用户拿来一篇 600 字的稿子，模型返回一份 400 字的「建议版本」。那不是批注，是替他写完了。用户既看不出哪里原来不好，下次也还是写成一样。

改法要短、要具体、要只针对被引的那一句。给方向、给一个可以照抄的短句就够了；整段该怎么组织，用批语说，别用改法写。

**合计上限仍是稿子的一半，但短稿至少给到 60 字。** 60 不是独立取的数，是 3 × 单条改法的地板（20 字），理由是结构性的：合计闸不该在三条改法各自只用单条地板额度时就先行拒收。三条短改法是制定这个地板时采用的最小可用形态，不是要求每份批注至少三条，也不保证任意三条合规改法的合计都能通过。长稿那一侧不受影响，走的仍是比例，稿子越长合计预算越宽——地板只托短稿这一端，没有另加总量天花板。

## 版本纪律：稿子只由用户改，历史只增

**脚本不改稿子，你也不改。** `draft.*` 从 `init` 落地那一刻起就是只读的。批注不合格就改 `inbox/marks.json`，永远不是改稿子去迁就批注。用户要改稿，让用户自己改，改完把新版本重新交进来。

**新一版走 `init --from`，不覆盖。** 稿子逐字没改就不算新一版，脚本会直接说（目标后缀也须相同）。同一个 slug 再跑一次 `init`，脚本把上一版的稿子、批注、红笔页整个搬进 `history/v<N>/` 再写新稿。`history/v<N>/` 已经存在就直接报错，不覆盖——历史只增不改，这样才能回头看每一轮改了什么。

**`marks.json` 与 `review.html` 是脚本的产物，不是可编辑的文件。** 手改任何一个，`check` 都会逮住：它会重跑闸门、重算锚定率、把红笔页重新渲染一遍逐字节比对。想让页面上的字变一变，只能改 `inbox/marks.json` 再 `review`。

**新一版做完之后跑 `stats`。** 它会拿上一版通过的批注去新稿里找，报出「上一版的 N 条这次消失了」。消失的那几条就是这一轮真正改动到的地方——这是唯一能说明「改了没有」的客观说法，比对着两版稿子凭感觉说强。

## 比例、地板、天花板，三个数缺一不可

设计比例预算时，比例、地板、天花板三个方面都要交代：**比例**给中位材料定形状，**地板**给短材料兜底，**天花板**给长材料收口。对单条改法，三个数缺一不可；只给比例，短引文可能容不下一句短改法，长引文又会带来过宽预算。若某一道闸不设固定天花板，也必须明说它的适用范围与取舍，不能把比例本身当作封顶。

red-pen 自己的实测语料暴露了这个问题。单条改法闸最早只声明了一个比例：改法不超过「引文字数 × 3」。引文越长预算越宽，引一整段就能还一整段——而这正是批注纪律要拦的事。现在单条预算补齐地板与天花板，限制长建议；这仍不等于机器能识别所有重写。合计预算则保留比例与地板，没有独立的固定天花板，长稿仍可容纳更多分散的短改法；每条还要过单条闸，整份还要过条数闸，不能据此拼出完整新稿。两段纯函数如下，连同常量可以整段搬去别处用：

```python
# 单条改法的字数预算：引文字数 × 3，夹在地板与天花板之间。
# 地板保住英文短引文（「Hi Dana,」只有 2 个字，乘出来写不完一句话），
# 天花板限制长建议，不能替代不代笔的纪律。
FIX_MAX_RATIO = 3
FIX_MIN_UNITS = 20
FIX_MAX_UNITS = 40
def fix_budget(quote_units):
    return min(max(FIX_MAX_RATIO * quote_units, FIX_MIN_UNITS), FIX_MAX_UNITS)


# 全篇改法合计的字数预算：稿子的一半，短稿另有一道地板。
# 地板只托短稿那一侧 —— 长稿走的仍是比例，稿子越长预算越宽，
# 这里没有新设总量天花板。
FIX_TOTAL_RATIO = 0.5
FIX_TOTAL_MIN_UNITS = 60
def total_fix_budget(draft_units):
    return max(int(draft_units * FIX_TOTAL_RATIO), FIX_TOTAL_MIN_UNITS)
```

两个函数都是纯函数：进去一个字数，出来一个字数，不读文件、不看 brief、不认语言。搬走时记得连同「字数怎么数」一起搬——预算的单位是主尺数出来的字数，换一把尺，预算参数的含义就变了。

单位说明：`unit_len` 本轮放在 `scripts/redpen.py` 里，闸门与 `init` 都从那里取；将来若有别的脚本也要按同一把尺数字，再谈把它挪进 `scripts/anchor.py`。

## 不打分

red-pen 只说哪一句、什么问题、怎么改。它不给分数、不给评级、不给「整体印象」，结果 JSON 里也没有放这些东西的地方。稿子好不好由用户自己判断，红笔的职责是把可改的地方指出来。


## 闸门零：收稿

格式准入挡的是**承诺的意义**：脚本本来就不执行稿子里的代码，格式白名单不是安全边界。若 `draft_text` 只是一屏 RTF 控制字，「引的是原文一字不差」仍可字面成立，却失去了改稿意义。因此编码兜底与格式准入必须一起落地：此前挡住二进制的只是 UTF-8 解码失败的副作用，只放宽解码而不加准入会倒退。

原稿无 BOM 且严格 UTF-8 读不出时，只猜一次 GB18030。它覆盖 GBK，再并列 GBK／CP936／GB2312 没有必要；增加 Big5、Shift-JIS、CP1252 只会增加没有优先级依据的误判。猜了必须明说，把正文开头两行交给用户核对；读出来是乱码就停下，不能继续批。brief 与批注 JSON 仍要求严格 UTF-8，原稿兼容不等于载荷编码放宽。

**不做乱码自动判定，因为没有可靠信号。** 已有试验的三个候选信号在真 GB18030 稿与三种误读情形下既逮不全，又都有正当的假阳性。在一个承诺确定性闸门的 Skill 里，造一道逮不全又会误伤的假闸门，比诚实地说「我猜的、你看一眼」更糟。这是永不做的边界，不增加启发式乱码闸。

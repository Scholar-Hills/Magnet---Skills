# 自批纪律（self-grader）

自批最容易坏在一个地方：批的人和被批的人是同一个，谁都愿意听好消息。模型也一样——
让它给自己刚读过的一段话打分，它倾向于找出这段话的优点。这份 Skill 的全部设计只回答
一个问题：**怎么让「分数」这个数字承担代价。**

代价的形式是闸门。闸门分两类：一类与 rubric-grader（老师批一叠作答）逐条相同，
是「判定必须有原文撑着」这件事的公共部分；另一类是自批场景独有的，用来堵住
「自己给自己放水」的那几条路。下面把两类都写清楚，以及为什么这样定。

## 一、共用闸门：判定要有原文撑着

这几条与 rubric-grader 同口径。两个 Skill 各自独立安装，代码是各带一份，
但行为必须一致——同一份作答、同一张条目表，两边跑出来的结论应当相同。

**1. 上下文哈希。** 结果里的 `context_hash` 必须等于脚本此刻用题目、评分标准、条目表、
这一稿作答重算出来的值。它挡的不是笔误，是两件真事：*没跑 `context` 就凭印象写结果*，
以及*材料改过之后拿旧结果接着用*。哈希对不上就是这两者之一，没有第三种可能。

**2. 键白名单。** 顶层恰好五个键，条目三个键，批注三个键，多一个就拒收。
听上去苛刻，理由很实在：一旦允许「多带点字段没关系」，模型就会开始自己发明字段，
把不敢写进 `points` 的分数写进别的名字里，而没有任何一条闸门认识那个名字。

**3. 分数与判定一致。** 条目标了分值时，`points` 必须恰好等于命中给满、部分给一半
（向下取整）、未命中给零的合计。这条闸门让「分数」不再是一个可以直接下笔的数字——
想给高分，就得先在某个具体条目上写下「这条命中了」，而那句话是要负责的（见第 4 条）。

**4. 证据锚定与降级。** 判 `hit` 或 `partial` 必须给引文，引文必须能在这一稿作答里
定位到。定位由引擎做：空白折叠、弯引号与破折号归一、大小写不敏感、剥首尾标点、
头尾锚定，能给的宽容都给了；仍然找不到，就是**这句话作答里根本没有**。
这时脚本把该条降为未命中，并看分数变没变：变了就整份退回重批。

  注意脚本**不会**替你把分数改小。它只说「按你自己给的判定和引文，这个分数站不住」，
  改哪一头由人决定：换一句真的在作答里的引文，或者如实判未命中。自动改分等于替
  批改者认账，那就成了脚本在批改。

**5. 批注要能落回原文。** 每条批注要有引文与至少 6 字的批语；条数有上限；
两条批语一字不差算重复；锚不到的批注比例超过上限就整份退回。前三条防的是凑数，
最后一条防的是「凭印象引用」——引文写得像作答里的话但不是原话，是模型最常见的失真，
锚定率是唯一能机器判定它的指标。

**6. 总评的长度与形状。** 60–200 字（英文按词），且不许出现「第 N 题」式的逐题复述。
太短是套话，太长是把作答重写一遍，逐题复述是把评分标准再抄一遍——三种都不是总评。
脚本只查长度与形状，**不查里面写了什么**：写得好不好不是机器能判的，别假装它能。

**7. 空心提示（只提示，不拦）。** 所有引文都短到不超过 6 字、批语又和作答没有一个
三字片段重合——这一份批注多半没读作答。脚本说一句就过，因为它也可能是真的：
一份极短的作答本来就没有长句可引。判断留给人，提示留给脚本。

## 二、专有闸门：自批场景的四条

### 1. 基线闸——先证明它不会白给分

**先批三份假作答，三份都必须 0 分、条目全部未命中，才准批真作答。**

三份是脚本生成的，不是你写的：空文件、题面原样回贴、一段与题目毫无关系的固定文字。
它们的作用不是练习，是**给这一轮的批改标准做一次校准**。如果一份空作答能拿到分，
或者把题目抄一遍就能命中某个条目，那么真作答拿到的分数同样没有意义——它测的不是
你写得怎么样，是这套标准有多松。

这是本 Skill 里唯一一条「不通过就整条流程停下」的闸门。它替代了 rubric-grader 里
老师给的满分范例与残缺版：一个人自批时没有第二份材料可以对照，只能让脚本造出
必须得零分的那三份。

盖章之后还有两道持续有效的闸：题目、评分标准、条目表任一改过，盖章作废（材料换了，
校准就过期了）；三份基线的 `answer.md` 必须与脚本算出来的正身逐字相同（把基线换成
真作答再让它「过基线」这条路要堵死）。

### 2. 同稿闸——一字未改的稿子不该评出两个分数

新一稿的作答与上一稿哈希相同时，分数必须相同，否则拒收。分数不一样只有一个解释：
标准在飘。同稿通过时那一行 `progress` 会标 `sameDraft`，走势不把它算成一次进步。

### 3. 重批闸——同一个 attempt 重批，分数也不许换

比同稿闸更近的一种放水：作答一个字没动，只是把 `inbox` 里的结果改了改再跑一次。
脚本记着这个 attempt 上次批出来的 `answer_hash` 与 `points`，作答没变而分数变了就拒收。
真的判错了，先说清上次哪一条判错、为什么，改完再批——**先有理由，再有新分数**，
不是先有想要的分数再倒推理由。

### 4. 无分值时的两条底线

条目表不标分值时，共用闸门第 3、4 条算不出「降级该扣多少」，整条让开。这时保留两条
底线兜住最坏的情况：引文一锚不到就整份退回（宽容不到「反正也算不出扣几分」的地步），
以及条目全部未命中却给了分——这个分数没有任何条目撑着，直接拒收。

这也是为什么**建议给条目标分值**：不标不是不能用，是能拦住的东西少很多。

### 补充：分数下降只提示不拦

改完一稿分数反而低了，脚本提示一句「核对一下是不是这次批得更严了」就放行。
改稿之后掉分是真会发生的事（把一段模糊的话改成明确的话，可能反而暴露了错误），
拦下来只会逼人把分数往高了写。

## 三、给 Agent 的几条硬规矩

- **不代写 `answer.md`。** 用户明确要求看范文时，另写一份并说清「这不是评分标准，
  只是一种写法」，写完提醒他这一稿的自批已经失去意义，换一道题再练。
  帮助分三档，一次只上一档：先指方向 → 再给关键判断 → 明确要求才给范文。
- **不内置评分标准。** 用户没带标准时帮他把手头的材料整理成条目表，或者陪他自己写一份，
  但不要凭记忆报出任何机构的评分细则——记错了比没有更糟。
- **不手改 `progress.md` 与 `result.json`。** 这两份是脚本的输出，`check` 会逐字对账。
  想加备注就另开一个文件。
- **不改脚本让题目通过。** 闸门拦下来的时候，要改的是结果，不是闸门。
- **如实报告。** `grade` 退出 1 就说「没过，卡在哪一条」，不要重跑几次挑一个能过的说法。

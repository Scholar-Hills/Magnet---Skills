# essay-sections 的纪律：每一条为什么在这儿

格式契约在 `workspace-format.md`，这份讲的是纪律——每条闸门拦的是什么、为什么值得拦、被拦了该怎么办。脚本行为改了，这两份文件与 `scripts/selftest.py` 要在同一个 commit 里一起改。

## 0. 分段这个抽象

一篇 = **开头 + 若干子问题段 + 结论**，三类段落同权：每一段都是可评审、可查、可反思的单位，开头和结论不是附属品。

这么切有两个好处。一是评审有了落点：「第三段跑题了」比「文章中间有点散」可操作得多。二是改稿有了边界：你改第四段，只有第四段的分数过期，别的段不受牵连——而如果按整篇打分，改一个字全篇的分数都要重来。

代价是它对「结构本来就不清楚」的稿子帮助有限。拆不出子问题的稿子，拆出来也只是把混乱平均分成八份。这种时候先想清楚每段要回答什么，再回来贴稿。

## 1. 两个入口，中途不能换向

| 入口 | 什么时候用 | 怎么走 |
|---|---|---|
| **从已有稿**（主入口） | 已经写完一稿，想知道哪段站不住 | `import` → 模型回分组 → `assemble` →（可选）`outline add` 补子问题 → 逐段 `context` + `review add` |
| **从题目** | 只有题目，还没动笔 | `outline add`（初始 6–10 条）→ 脚本建出分区骨架 → **用户自己写每一段** → `context` + `review add` |

- `import` 在已经有分区的工作区上**直接拒收**。已经拆过段还想重来，另起一个 slug——盖掉已有账本比重跑一遍贵得多。
- 反过来也一样：先贴稿再补子问题走的是 `outline add` 的 **bind 模式**，条数**必须正好等于正文段数**。给多给少都拒收，因为子问题是按位置绑到段上的，数目对不上就会错位。
- 从题目入口建出来的 `sections/*.md` 是空文件。**脚本不写正文，Agent 也不许写正文**，那是用户的活。

## 2. 导入：一个字不改，只是拆开

`import` 只做两件事：把原文原样存下来，再切成块、记住每一块在原文里的**字节区间**。给模型看的只有块号与 46 字预览，模型回的只有分组（哪几块归 `intro`、哪几块归 `body[0]`……）。`assemble` 拿着分组，**按偏移把原文切回来**——每一段都是原文的一段连续切片，不是模型转述的版本。

所以「一个字没改，只是拆开了」不是一句宣传语，是一条可验证的恒等式：把全部分段与全部「未纳入」片段按偏移拼回来，必须逐字节等于 `source.txt`。不等就退出 1，**一个字都不落盘**。

### 「未纳入分段」为什么必须逐条列出来

分组的时候总会剩下东西：标题、没分到段的块、包裹层、段间空行、docx 里的表格与文本框。这些都写进 `split-report.md` 的「未纳入分段」，**有字的片段连原文一起列出来**。

不静默丢，是因为静默丢最贵：用户看着八张卡以为整篇都在里面，其实那段关键的注释在导入时就没了。宁可让他看见一串「未纳入」，自己决定要不要手动补进某一段。

**docx 特别提醒**：表格与文本框里的字被搬到正文之后的附录区，**不在原来的位置**，并且必然出现在「未纳入分段」清单里。排版复杂的稿子会看到很长一串。这不是脚本读丢了，是它不敢替你决定这些字该插在哪一段。真在意排版的话，先在 Word 里另存为 `.md` 或 `.txt` 再进来。图片、脚注与修订痕迹读不了。

模型回的分组不合格（不是对象、缺 `body`、一个有效块号都没有）时，脚本**整段导入**：全文归成一段，标 `fallback`。宁可给一张大卡，也不按猜测乱切。

## 3. 评审的准入：没跑 `context` 就不许写

每条评审都要带 `contextHash`，它是这五样东西的哈希：**这一段的纯文本、它的子问题、全篇主论点、背景（文体 / 级别 / 场景 / 目标字数 / 说明）、装配好的反思包**。

- 缺 `contextHash` → 拒收。**这一条挡的是「凭印象评」**：没跑 `context`，就不可能有那个哈希。
- `contextHash` 对不上 → 拒收，并告诉你是哪一类东西变了。原文改过一个字、背景改过、场景从限时改成不限时、目标字数改过、新写了一条反思，都会让它变。
- 分区纯文本不足 10 字 → `context` 就不给包，`review add` 也不收。**空段不给评**：给一段还没写的文字打分毫无意义，还会让走势图上多一个假点。

哈希只有一个来源，就是 `context` 的输出。不要手抄，不要自己算，不要从上一轮对话里翻。

## 4. 三个维度与综合分

| 维度 | 一句话 |
|---|---|
| `language` | 这一段的句子本身立不立得住：读得顺、说得准、没有含糊过去的地方 |
| `answersSubquestion` | 它有没有回答自己那条子问题（开头和结论就看有没有做到自己那件事） |
| `advancesThesis` | 它有没有把全篇的主论点往前推一步，而不是原地复述或者跑到别处去 |

各一个 **1–5 的整数**。布尔、小数、字符串、负号、越界都不算，多一个维度也拒收。

**综合分由脚本取三维均值四舍五入，载荷里不许出现。** 这一条不是洁癖：手填的综合分会跟三维分对不上，而反思的触发、走势的画法、`check` 的复算全都拿它当依据。让它只有一个来源，是让后面所有东西可复算的前提。

评审不合格时**最多重出一次**。两次还不过，就如实告诉用户「这一段我没评成，卡在哪一条」，不要改闸门、不要挑一个能过的说法糊过去。

## 5. 证据引用：证明你读了原文

每份评审至少 1 条 `quotes`，逐字引自这一段。

- 空白归一之后必须是该段纯文本的**子串**。顺手润色过的引文对不上，会被逮住。
- 彼此不许重复。
- 单条与合计长度都不许超过该段的 **40%**（分母是去掉全部空白之后的纯文本长度，跟卡片上显示的字数不是一个口径）。超了就是在复读原文，不是在评审。

这一条能证明的和不能证明的，说清楚：**它证明的是读了原文、没有抄评审，不证明评得对。** 引用对得上、长度也合规的一份评审，仍然可能评得很浅。空心闸只能机检下面这些，检不出「认真读了但看得不深」：

- 两个分区的评语**一模一样** → ERROR，整份拒收。八段贴同一份评审等于没读。
- 评语跟这一段没有一处三字重合，而且只引了一小截（≤10 字）→ WARN `thin-quote`。
- 三维分与另一段完全相同、评语词集重合度 ≥0.6 → WARN `look-alike`。

WARN 不拦入账，但会记进账本行的 `flags`，`report` 上打标，`check` 里也会念出来。看到它就回去重写，别当没看见。

## 6. 账本只增不改

评审、反思、拆题各是一条链：每行带 `seq`、`when`、`prevHash`（上一行整行的 sha256），脚本以追加模式写，`chains.json` 记链尾。「最新」永远由脚本从链尾算，不另存一份。

- **Agent 只能往 `inbox/` 放载荷**，脚本消费完立刻删掉。账本、`essay.json`、`report.html` 全是脚本的产物，手改一律会被 `check` 逮住。
- **`sections/` 只有用户能动。** `status` 逐段打印哈希与 mtime，就是给用户核对「有没有人替我写」用的。
- 同一稿重复评审会标 `sameDraft`，走势上画空心点、不加长度——**同稿重评不算进步**。想让走势往前走，就得真的改稿。

这套账本能证明什么，也说清楚：账本挡的是不知情的手改；知道 `chains.json` 存在的人两处一起改就能过。它证明的是账本没被顺手改过，不是不可伪造。只要 `chains.json` 还在，行少了就是硬错——`--rebuild-index` 不会替你抹掉少掉的行，只修写盘被打断时落后的索引。

## 7. 反思：只在评得极端时才要求写

区域反思**只有**在该段最新一条评审的综合分 **≤2 或 =5** 时才收。触发分与对应的行号由脚本从账本取，载荷里带 `atScore` 直接拒收。

为什么卡这两头：中间分数写反思容易写成「还行，再改改」，没有信息量。评到 2 分说明这一段确实出了问题，趁着刚被指出来写一句，比事后回忆准；评到 5 分说明这次做对了什么，值得记下来复用。

反思自带当刻的分区纯文本快照，所以它**钉在那一稿上**：以后你把这一段改了，反思还在，它记的是「当时这一段是这样、当时评了 2 分」。快照超过 20000 字就不再存、不再比对（否则长段落会永久显示「原文已修改」）。

总反思随时可写，不需要触发。

反思写完之后会进后续评审的上下文包（最多 3 条，同段 > 总反思 > 其他段，组内新→旧）。**这意味着写完反思，之前跑过的 `context` 就过期了**——这是设计如此：评审者应当知道作者已经反省过什么。

## 8. 荐读：默认没核实

`reading add` 记一份材料，`verified` 缺省 `false`，卡片上标「引用未核实」。

**脚本不联网，也不会替你核实任何出处。** 模型给出的书名、作者、年份都可能是编的。所以每次交付荐读时，Agent 都要明说一句「这几条我没有核实，请自行检索确认之后再引用」——这不是免责声明，是这一步唯一诚实的说法。

同一分区里标题相同（小写比对）的材料拒收：换一个角度，或者换一段。

## 9. 版本与「原文已修改」

`version` 给 `sections/` 拍一张逐文件快照，编号按已有最大号 +1。账本行记下写它时的版本号。

用户中途手改 `sections/` 之后旧评审失效，是**正常现象**，不是错误。`status`（一行 `** 原文已修改`）、`context`（`previousReview.segmentChanged`）、`report`（灰显的卡片 + 徽章）三处都会标出来，`check` 也会报 WARN。看到它就知道：这一段的分数是给旧稿的，要么重跑一次评审，要么别拿它当数。

## 10. 与 red-pen 的分工

这份 Skill **只判分与举证，不改句子**。评审载荷里出现 `improved` 或 `rewrite` 字段直接拒收。

要改句子，把那一段丢给 **red-pen**：它逐句批注，每条批注带一句一字不差的原文引文，由脚本钉回原文，钉不住的老实标成「未能定位」；它不打分，也不给整段重写。两件事分开做的理由很简单——「这段没答自己的问题」和「这句话该怎么写」是两种判断，混在一起给，用户既看不出问题出在哪，也学不会下次怎么改。

首版**没有原创性检查，也不给改写建议**。卡片上只有三个 1–5 的格子和一段评语，不产生任何比例、百分比或者相似度分数。这不是「暂时没做」的功能缺口，是刻意的形态选择：三个格子说的是这一段答没答自己的问题，跟比对外部文本没有任何关系。
